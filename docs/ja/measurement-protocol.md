# 測定プロトコル

ユニットを測定する順序です。各段階は前の段階が書いたファイルによって狙いを定めるため、順序は便宜ではなく手法の一部です。順序を外して実行した段階は、このアーカイブが記述できないものを測ることになります。

2 台のユニットを比較する主張は、どちらもこの方法で測定されていることに乗っています。異なる方法で測定したユニットも単体としては記述できますが、比較には参加できません。

## どの段階よりも前に

すべてのコマンドは、何かを書き込む前に MIDI 経路を検証します。自己診断は単独で先に実行してください。そうすることで、失敗が「たまたま実行していた段階の失敗」ではなく「経路の失敗」として読めます。

```sh
rye run soundings selftest --audio "<audio interface>"
```

自己診断の合格が示すのは、ハーネスがユニットを読めることだけです。そのユニットを探索して安全であることは示しません。すべての段階に共通して 2 つの制約があります。

- **一括要求は 64 バイト以下に保つ**。これを超える要求は、ユニットの応答を完全に停止させることが実測されています。復帰には電源の再投入が必要です。
- **応答することが分かっているアドレスを定期的に問う**。応答しなくなったユニットは、存在しないアドレスの空間として読めます。沈黙を不在として扱う探索は、何も測らないまま正常終了します。

## 段階

### 1. 識別

```sh
rye run soundings identity
```

Identity Request に対してユニットが返すものを記録します。返答は背面の定格表示、測定チェーン、ユニットの設定とともに `meta.json` へ verbatim で入ります。以降に測定するものはすべて、この記録にスコープされます。

### 2. アドレスマップ

```sh
rye run soundings sweep --out data/units/<unit-id>/address-map.json
```

どのアドレスが応答するかをユニットに問います。このマップは文書が列挙するものではなくユニットが答えたものであり、以降の段階はこれを狙って実行されます。マップに無い領域は、以降に測定されるすべてから外れます。

### 3. 電源投入時の状態

```sh
rye run soundings power-on --map data/units/<unit-id>/address-map.json \
  --unit-id <unit-id> --out data/units/<unit-id>/power-on-state.json
```

空間を 2 度読み取り、何も書き込みません。得られるのは、ユニットが電源投入時に置かれている状態です。

**書き込みを行う段階より前に実行できる、最後の段階です**。段階 1 から 3 は読みしか送らないため、sweep の後に取得しても電源投入時の状態のままです。段階 4 以降はユニットへ書き込むので、そこから先は次の電源再投入まで取得できません。マップは sweep をやり直せば作れますが、この取得はやり直せません。

この実行は、電源を入れた直後のユニットと、以前の実行が書き込んだ後のユニットとを区別できません。どちらも読みに対して同じように答えるためです。そのため記録するのは、実行前に何をしたかについての操作者の申告であり、それを申告として明示したうえで、この実行自身が言えること — 自らは何も書いていないこと — を併記します。

2 回の読みが食い違ったアドレスは、解決せずに一覧として残します。どちらかに決めるには 3 度目の読みが必要であり、誤った決定は後から見えません。そのバイトは、次にこの取得と比較されるリセットによって変更されたもの、として読めてしまいます。以降のリセット測定はすべて、このファイルと比較されます。

### 4. 窓

```sh
rye run soundings window-probe --stores <addr> <addr> <candidate>...
```

自分の値を保持しているブロックと、別のブロックの値を見せているブロックとを判別します。アドレスが何を保持しているかを解釈する段階より前に実行します。窓は、書き込んで読み戻す方法では格納と区別できないためです。書き込みが窓を向け、読みがそれに追従するので、そのアドレスは与えられたとおりの値を答えます。

窓と判定されたブロックは、それを記述する記録の中で名指しされ、以降の段階では除外されます。除外しなければ、同じストアを、その素性を残さない名前で何度も測ることになります。

### 5. 受理される値

```sh
rye run soundings write-probe --map data/units/<unit-id>/address-map.json \
  --resume --out data/units/<unit-id>/write-probe-wholemap.json
```

各バイトを単独で書いて読み戻し、そのアドレスが何を受理し、何をクランプし、何を拒否するかを記録して、元に戻します。領域は終わった順に書き出されるため、中断した実行は最後に完了した領域から再開できます。

1 バイト読みに応答しないアドレスへは書き込みません。戻すものが存在しないためです。それらは skipped として記録します。そのうちどれが未定義で、どれが「より大きなブロックとしてのみ到達できる」ものなのかは、この段階では決着しません。

### 6. 独立した格納

```sh
rye run soundings hold-probe --map data/units/<unit-id>/address-map.json \
  --out data/units/<unit-id>/hold-probe-wholemap.json
```

隣接するアドレスへ異なる値を与えてから、どれも読まずに全部を読み戻します。これにより、1 つのセルに支えられた連続アドレスと、それぞれが別のセルである連続アドレスとを分離できます。順序そのものが手法です。書きと読みを分ければ、近傍へ最後に書かれた値しか見せないアドレスはその 1 つの値を答え、隣接アドレスはそれぞれ自分の値を答えます。

この段階は、別のブロックをミラーしているブロックを見つけません。それは段階 4 が問うことです。

### 7. エイリアス

```sh
rye run soundings alias-scan --map data/units/<unit-id>/address-map.json \
  --kind cc --out data/units/<unit-id>/cc-aliases-ch1.json
```

ある系統のメッセージを 1 つずつ送り、その前後でアドレス空間を差分して、メッセージが到達する格納場所を特定します。系統ごとに 1 回ずつ実行します。`cc`、`nrpn`、`rpn`、`channel`、`drum-nrpn`、および SysEx による書き込みの `address` です。

**マップ全域を監視してください**。`--prefix` の既定はそうなっています。1 つのブロックに限定した走査は、そこで得られる否定的所見のすべてをそのブロックへ限定します。「このメッセージはどこにも格納されない」という記録は、そのとき「見た範囲のどこにも」という意味になります。

`--kind address` は、先行する走査が到達を確認したアドレスへ書き込み、その場所に第三の入口があるかどうかを問います。書き込み先は、そのユニット自身の記録から取ります。

```sh
rye run soundings alias-scan --map data/units/<unit-id>/address-map.json \
  --kind address --addresses-from data/units/<unit-id>/cc-aliases-ch1.json \
  --out data/units/<unit-id>/sysex-aliases-ch1.json
```

### 8. リセット

```sh
rye run soundings reset-probe --baseline data/units/<unit-id>/power-on-state.json \
  --map data/units/<unit-id>/address-map.json \
  --write-probe data/units/<unit-id>/write-probe-wholemap.json \
  --out data/units/<unit-id>/reset-probe.json
```

各リセットの前に状態を壊し、後で空間を読みます。これにより、文書がリセットについて述べていることではなく、そのリセットが実際に復元するものを測定します。マークを置くのは、書き込み探索が「任意の値を受理する」と判定したアドレスに限ります。クランプするアドレスは元の値を保ったままかもしれず、壊されなかったバイトはリセットについて何も語らないためです。

すべてのリセットは同一のリセットを前置して実行します。そうすることで、結果を互いに比較できます。前置しなければ、各結果は「直前のリセットがたまたま残した状態」を基準に読むことになります。

### 9. 音色とエフェクト

```sh
rye run soundings tone-map --out data/units/<unit-id>/tone-map-m0.json
rye run soundings efx-map --out data/units/<unit-id>/efx-type-map.json
```

各音色と各挿入エフェクトを要求し、受理されたかどうかを読み戻します。走査前に標本抽出を行うマップは、その標本抽出を但し書きとして持ちます。`--exhaustive` は全バンクに 128 プログラムすべてを問うもので、但し書きの付かない唯一の形式です。

### 10. 再現性 — あらゆる音の比較より前に

```sh
rye run soundings repeat --audio "<audio interface>" \
  --out data/units/<unit-id>/repeatability-p0.json
```

同一の刺激を 2 回鳴らし、2 つのテイクがどれだけ一致するかを測定します。この数値が、以降のあらゆる差分測定の床になります。床を下回る領域では、「差が無い」と「差を見る解像度が無い」は同じ読みです。

床はユニットと測定チェーンの両方の性質なので、ユニットごとに測定し、チェーンを変更したときは測定し直します。

### 11. 可聴な差

```sh
rye run soundings contrast --cc 91 --audio "<audio interface>" \
  --out data/units/<unit-id>/audible-cc91.json
```

1 つのパラメータの 2 つの設定を、再現性の床を基準に比較します。これにより、ユニットが格納するパラメータと、それを通して実際に聞こえるパラメータとを分離できます。格納されていて可聴でないパラメータは存在します。アドレス空間側の段階はその区別をつけられず、この段階はつけられます。

`transfer`、`motion`、`decay` はそれぞれ、アナログ経路、時間変化するエフェクト、エフェクトの減衰を測定します。`motion` と `decay` はテイクを読むだけで、ユニットの接続を必要としません。

### 12. ブロック全体

```sh
rye run soundings plan data/units/<unit-id>/write-probe-wholemap.json "40 11" \
  --out plan-40-11.json
rye run soundings block plan-40-11.json <plain records> --gesture <gesture records> \
  --balance <balance record> --out data/units/<unit-id>/audible-part-1.json
```

マニュアルが面白そうに見せたアドレスではなく、ブロック内の全アドレスに対して「変えると音が変わるか」を問います。2 パス構成です。まず素の打音、次にそれで聞こえなかったアドレスを、設定の後にメッセージを動かした状態で問い直します。メッセージが受信されるかどうかだけを決めるパラメータは、素の音では受信するものを持たないからです。

各アドレスを問う値の組は文書ではなく書き込みプローブから来ます。ブロックは、たまたま存在する記録の数ではなくプランに対して数え合わせます。47 アドレスのブロックに 45 個の記録がある状態は、完全な回答とまったく同じ見た目をするからです。

**ブロック自身が「聞いている」と言うチャンネルで問うこと。** そのバイトはブロックの中にあり、ユニットが答えてくれます。他のチャンネルに出した刺激は、そのアドレスが宛先としないパートに問うことになり、ブロックの全アドレスが「聞こえない」と答えます。

**受理範囲だけから選んだ組では、チャンネルのバイトを問えません。** 書き込みプローブはそのアドレスが何を受け取るかを報告しますが、刺激がどのチャンネルにいるかは知りません。組の両方の値がパートを発音中のノートから引き離す場合、どちらの設定も無音になり、実行は測定を拒否します — それは「値の組の選択が悪い」ではなく「収録の失敗」に見えます。そうしたアドレスは、そのパート自身のチャンネル対 off で問います。

## 可聴という判定の読み方

判定は 3 つの経路で立ちます。形が変わった、レベルが変わった、あるいは片方の設定のテイク同士が他方よりはるかに一致しない。前の 2 つは音そのものを測っています。3 つ目はばらつきを測っており、ばらつきはパラメータ以外のものからも生じます。

**一致度だけに乗る判定は、安定している側が絶対値として安定していることを要求します。** 比較対象は他方の設定ではなく、同じアドレスに対する素の打音自身の数値です。ゲートは、それが遮る側を素の打音と同じように再現させます。自由に走る位相からの 2 つの引きは、どれだけ離れていても何も意味しません。

**刺激は、その判定が数えられる前に、自分自身の再現性を確立しなければなりません。** 段階 10 が測るのは 1 つの刺激についての床です。複数の声部を鳴らす刺激は、トリガが固定できない相対位相を持ちます。トリガのばらつきが発音中のノートの 1 周期より広い場合、位相はテイクごとに自由になり、レベルがそれに従って動きます。あるユニットでの実測: 素の打音が 56〜62 dB で一致する一方、2 音の刺激は 1〜66 dB に散り、その 84% が 10 dB より悪い値でした。この刺激が報告したものは、二度目に問うと何一つ残りませんでした。テイク数を倍にしても改善しませんでした。

**ちょうど 1 つの刺激だけが目撃した判定は、公開前に問い直します。** ある 3 ブロック掃引では、この種の判定がすべて再現しませんでした — 最初のパスが最も健全に見えたものを含めてです。問い直しの費用は、存在しない結果を公開する費用に比べて安上がりです。

**同じパラメータを持つ 3 つのブロックは、3 回の引きです。** 1 つのブロックに現れて他に現れない判定は、パート間の差か（パラメータは通常そのような差を持ちません）、再現しなかった測定のどちらかです。その区別には問い直しが要り、議論では決まりません。

## すべての記録が持つもの

何も見つけなかった段階は、その実行が何かを見つけられたはずである場合にのみ読む価値を持ちます。そのため各記録は、その実行が備えていたコントロールを明示します。

- **陽性対照**。最初の刺激の前と最後の刺激の後に送ります。1 回だけ送られた対照は、その実行の残りについて何も語りません。
- **試験対象の系統が実際に到着したかどうか**。陽性対照はコントロールチェンジであり、他の系統のメッセージが通ったことは示せません。これを欠く実行では、すべての否定的所見はユニットではなく経路についてのものになります。
- **書き込んだブロックの外への着弾を報告できたかどうか**。あるアドレスへ書いてそのアドレスしか動かなかったという実行は、そこをミラーするものが無い証拠になりますが、それは他所へ着弾していたら報告されたはずである場合に限ります。
- **何を復元したか、そして何を対象から外したか**。実行が覆うのをやめた範囲は、その実行が述べることすべてに掛かる但し書きです。

## 何時間もかかる段階を実行する

ブロック全体を掃引する段階は何時間も走り、`procedures/` のドライバから駆動します。ここは追跡されています。1 台のユニットに固有のドライバは作業ノートであり対象外ですが、プロトコルの一部であるものはここに属します。他の誰も持っていないスクリプトで測定された 2 台目は、同じやり方で測定されたことになりません。

```sh
./procedures/part-block.sh "40 11" 0        # ブロックと、それが聞いているチャンネル
./procedures/stop-sweep.sh                  # 停止し、止まったことを証明する
```

**1 アドレスずつ、新しいプロセスとして実行します。これは実装の都合ではありません。** 無人の長時間実行が遭遇する 2 つの失敗はどちらもアドレス 1 つ分を丸ごと失わせ、うち一方はプロセスを即座に終了させます。したがって新しいプロセスとして問い直すことが、それに対する唯一の回復手段です。

**各段階は、前の段階自身の記録によって照準されます。** ジェスチャのパスが問う対象は `soundings block` が「まだ開いている」と名指ししたものであり、手で書くのではなくファイルから読みます。二度書かれたリストは二度下された判断であり、両者はずれます。照準となるべき記録が存在しない場合、段階は起動を拒否します。空のリストと落ちた読み取りは、次のパスに同じもの — 何も — を送るため、実行は「やることが無いパス」として報告してしまうからです。

## 測定チェーン

チェーンはプロトコルの一部です。インタフェース、ゲイン、結線、収録方法はユニット間で同一に保ちます。そうしなければ、2 台のユニット間のレベル比較を、2 つのチェーン間の差と区別できません。

やむを得ずチェーンを変更した場合は、その差異を `meta.json` の `measurement_chain` に記録し、そのユニットを含むレベル比較には「確立していない」と付記します。

実機を使う段階は直列です。オーディオインタフェースが 1 つ、ユニットが 1 台という条件では、前景の収録中に背景の実行が鳴り、再現性が静かに崩壊した数値だけが残ります。

この規則は破られる前に書かれていました。つまり書き留めるだけでは足りず、ハーネスが強制します。ユニットを駆動するコマンドは排他ロックを取り、2 つ目は起動を拒否されます。**拒否することが要点です。** 2 つ目の実行の側からは何も異常に見えません — ノートは鳴り、テイクは録れ、記録は普通の顔で出てきます。痕跡は 1 つ目の実行のテイクの中、もう一方のノートが、ノイズフロアを測るためのリードインに着弾している場所にしかありません。

**実行を止めるとは、その全プロセスを止め、かつ止まったことを証明することです。** ドライバは入れ子になっており、それぞれが一度に 1 段階ずつを起動します。したがって木の頂点を殺すと、殺された子が死んだ瞬間に親が次の段階を開始します。親を子より先に殺し、走査が空で返るまで繰り返し、止まったと証明できない停止は止まらなかったものとして扱います。生き残りは待機していません。ユニットにノートを鳴らし続けています。

**無人の長時間実行における 2 つの失敗は、アドレスについてのことではなく、その瞬間に機械が資源を渡さなかったことです**: 要求した長さより短く返ってきた収録と、MIDI 層がクライアントの作成自体を拒むこと。どちらもアドレス 1 つ分を丸ごと失わせ、後者はプロセスを即座に終了させます。したがってどちらも、新しいプロセスとして問い直すことで再試行します。何回の再試行が必要だったかは記録します。上昇する再試行率はチェーンについての事実だからです。
